# LifeOS: надёжная очередь обработки записей

## Цель

Запись дневника и задача её AI-обработки должны переживать перезапуск API-сервера. Пользователь видит готовый анализ только после успешного завершения задачи.

## Границы

- В очередь попадают только текстовые записи и расшифрованный текст голосовых записей.
- Оригинальные аудиофайлы не сохраняются и не загружаются в облако.
- Очередь не хранит сырой текст дневника и не логирует его.
- Пользователь получает только безопасный статус обработки, без внутренних ошибок провайдера.

## Архитектура

1. API сохраняет `life_record` и создаёт единственную задачу `processing_jobs` со статусом `queued`.
2. Воркер атомарно забирает одну ожидающую задачу и переводит её в `processing`.
3. Воркер получает исходный текст через `record_id`, запускает существующих AI-агентов и сохраняет артефакты.
4. При успехе задача получает статус `processed`; при ошибке — `failed`, счётчик попыток увеличивается, а текст ошибки обобщается.
5. Для одной записи действует уникальное ограничение: повторная отправка не создаёт второй задачи.

## Данные

Таблица `processing_jobs`:

- `id uuid` — идентификатор задачи;
- `record_id uuid unique` — ссылка на `life_records`;
- `user_id uuid` — владелец записи;
- `status text` — `queued`, `processing`, `processed` или `failed`;
- `attempt_count integer` — число попыток;
- `last_error_code text nullable` — только безопасный код ошибки;
- `created_at`, `started_at`, `completed_at`, `updated_at`.

RLS разрешает пользователю видеть только свои статусы. Сервер с secret key может создавать и обрабатывать задачи. SQL-функция `claim_processing_job` выполняет захват одной задачи с блокировкой строки, чтобы два воркера не обработали её одновременно.

## Ошибки и повтор

- Ошибка LLM или сети переводит задачу в `failed` без содержимого дневника в ошибке.
- Повторный запуск может перевести `failed` задачу обратно в `queued`; максимальное число автоматических повторов — 3.
- Если задача осталась в `processing` дольше заданного срока, служебный воркер может вернуть её в `queued`.

## Проверка

Автоматические тесты должны подтвердить:

1. одна запись создаёт одну задачу;
2. повторная постановка не создаёт дубликат;
3. захват меняет статус только с `queued` на `processing`;
4. завершение и ошибка не раскрывают сырой текст;
5. адаптер правильно формирует запросы к Supabase.

## Критерий готовности

После выполнения SQL-миграции в Supabase новая запись имеет надёжный статус обработки, а перезапуск API не удаляет ожидающую работу.
